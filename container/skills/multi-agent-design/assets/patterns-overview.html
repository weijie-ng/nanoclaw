Multi-agent design

Multi-agent patterns at a glance

When a job is too big or too mixed for one go, there are five shapes for splitting it up. Each has a cost, and reaching for the wrong one is how a simple request gets expensive. Here is what each shape is, what it is good and bad at, and when to pick it. Point at any pattern and ask me to walk you through it, or to build your task in one.

Two words run through the cards. A subagent is a helper that runs inside a single reply and hands its answer straight back, so it is cheap and nothing is left running. A standing agent is a separate assistant that keeps going between chats: every message to it is a fresh wake-up on both sides, which is what makes it dear. Most of these patterns have a cheap subagent version and an expensive standing-agent version of the same shape.

Chain

Also called prompt chaining.

A pipeline where each step takes only the previous step's finished output, not everything it knew: parse a document, pull the figures from the parse, then summarise the figures. Each handoff is small on purpose, which is what keeps it cheap.

Pros

  • Cheap: each stage is one in-turn subagent call with nothing left running to maintain.
  • Keeps context small: a stage carries forward only the last stage's output, so bulk never piles up in your head.
  • Fixed, predictable shape: the stages are known in advance and easy to reason about.

Cons

  • Only pays off if the handoff stays genuinely small; if a stage has to re-read what the previous one read, you split the work for nothing.
  • Should never be built from standing agents: a standing pipeline re-transfers the built-up context at every hop, a wake on each side per stage for no gain.
  • Errors travel forward: a bad early parse quietly poisons every later stage.

Use cases

  • Parse a document, extract the numbers from the parse, then summarise the numbers.
  • Translate text, then check the translation reads naturally, as two ordered passes.
  • Clean and normalise messy data, then run the analysis on the clean version.

Router

Also called routing.

One classify-then-dispatch step: look at the request, decide which category it falls into, and hand it to the specialist best suited to it, instead of making one generalist do everything. The cheapest router is just one agent picking a skill or a subagent brief by the request.

Pros

  • Tighter prompts per branch: each specialist carries only what its own category needs.
  • The cheap version is near-free: one agent picks a skill or a subagent brief for the category inside a single turn.
  • Clean separation of concerns when the categories are genuinely distinct.

Cons

  • Only worth it if the categories are really distinct; if they overlap, you paid a classification hop for nothing.
  • There is no live-dispatch primitive: routing among standing agents makes each dispatch a message, a wake on each side, and the router must already hold a destination row to every target.
  • No ack: with standing targets the router holds the correlation itself, and nothing tells it a branch went quiet.
  • Agents spun up just to be routing targets are usually the cheap in-turn brief-pick wearing a costume.

Use cases

  • Sort incoming questions into 'factual lookup', 'data crunch' and 'planning', and hand each to the matching brief.
  • Triage support messages: refunds down one path, bug reports down another.
  • Pick the right skill for a request (a document task versus a search task) before doing the work.

Fan-out / fan-in

Also called parallelisation (sectioning) or orchestrator-workers.

Split a job into independent pieces, run them at the same time, then gather the results into one answer. The pieces can be fixed in advance (sectioning) or decided on the fly (orchestrator-workers): same shape either way.

Pros

  • Parallel speed: N pieces run together inside one turn as subagents.
  • Keeps bulk out of your context: each subagent reads its slice and returns only the finding, not the raw material.
  • Good for genuinely independent facets that do not need to know about each other.

Cons

  • Fan-in is your job: nobody aggregates for you, so you hold the running answer and decide what to do if only some pieces have reported.
  • Parallel subagents share one workspace, so two writing the same file race and one wins silently: return findings, or give each its own filename.
  • The standing chief-and-workers version costs a wake on each side per worker, workers cannot reach each other, and there is no ack to tell a crashed worker from a slow one.
  • Standing each worker up needs admin approval unless your cli_scope is global; only worth it when the workers are real standing concerns, not just here to serve this request.

Use cases

  • Read six files and report which ones match a rule, one reader per file.
  • Summarise ten articles in parallel, then merge them into one briefing.
  • Check a claim against several sources at once, then weigh the results together.

Reflect-and-critique

Also called evaluator-optimiser.

One mind drafts, a different mind attacks the draft and feeds back, and you iterate to a clearly named stopping point. The critic must not be the drafter, and must not have seen how the draft was made: that blindness is the whole reason the second call exists.

Pros

  • Catches errors a single pass misses: the second mind is there precisely to find what the drafter cannot see in its own work.
  • Cheap as subagents: two-plus in-turn calls, a drafter plus a fit-for-purpose critic (a refuter for 'could this be wrong', a fact-checker for 'is it true', a verifier for 'does it meet the stated criteria').
  • Iterative refinement that measurably improves the output when the criteria are clear.

Cons

  • Needs a nameable exit and an iteration cap set before you start: 'until it is good' runs forever.
  • Only works if the critic is genuinely separate and blind to the draft's making: if the drafter grades itself, it is a single pass pretending to be a loop.
  • As standing agents each loop is two wakes and the draft travels by message, which is rarely warranted.

Use cases

  • Draft an argument, have a refuter subagent try to knock it down, revise, and stop when no new objection lands.
  • Write a claim-heavy summary, run a fact-check pass over it, then fix what fails.
  • Produce an artefact against a checklist, and have a verifier subagent confirm each criterion before it ships.

Consensus / debate

Also called parallelisation (voting).

Ask the same question several independent ways and then tally or weigh the answers, so a noisy or high-stakes judgement does not rest on a single attempt. Voting is independent one-shot attempts you count; debate adds argument across rounds.

Pros

  • Raises confidence on noisy or high-stakes judgements: several independent attempts beat one.
  • Cheap as a subagent vote: N runs of one prompt in a single turn, then you tally.
  • Diversity of approach surfaces answers a single run would miss.

Cons

  • Waste on anything with one deterministic answer: you pay N times for a result you would get once.
  • Subagents cannot talk mid-run (they return once), so a subagent 'debate' is really just one round of independent votes.
  • True back-and-forth needs standing agents: a wake per utterance per side, no shared transcript, replies landing in finish order not send order, any message holdable for approval.
  • There is no voting or quorum primitive: the chief tallies by hand, with no signal separating a crashed voter from a thinking one.

Use cases

  • Ask three independent runs to rate a risky decision, then go with the majority.
  • Generate several candidate answers to a fuzzy question and pick the best-supported one.
  • Sanity-check a judgement call by seeing whether independent attempts agree.
